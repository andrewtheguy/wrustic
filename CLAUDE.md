- no backward compatibility of any kind since it is a private and personal project.
- git is for tracking change logs, don't add any additional change logs on documentations or codes
- all read operations use rustic_core natively, never shell out to restic. Native write operations are allowed only under the restic-compatible lock module (src/lock.rs, docs/locking.md): currently snapshot delete + tag edits (lossless raw-JSON snapshot rewrite) + unlock. Prune shells out to the restic cli (a bundled restic in a restic/ subdirectory under the wrustic executable's directory wins over PATH; the subdirectory keeps it off the PATH the installers put wrustic on), with restic's cache pointed at a wrustic-private --cache-dir. Everything else that writes (init, backup, key management, repair, migrate, dev-flow repo setup) stays on the restic cli — from code, always via the secure spawn harness in src/restic.rs (restic::run pipes the password over stdin and credentials over env; never put secrets on argv)
- use restic --json output for parsing and avoid parsing human-readable output
- use this project root's tmp/ folder for dev/test data and workspace to avoid permission issues
- run cargo clippy and cargo test with --all-features after rust code changes, don't run cargo fmt because it affects diff
- for local testing, use alternative config dir such as cargo run -- --config-dir ./tmp/wrustic-sandbox so that it won't interfere production config in ~/.config/wrustic
- **To check a change against Windows CI before pushing, run `.\ci\windows\remote.ps1`.** It ships the *working tree* — uncommitted changes included — over ssh (the `winci` alias) to the Hyper-V CI VM and runs the workflow's steps there: clippy with `-D warnings`, `cargo test --all-features`, and a release build with `keychain,smb-tun`. `remote.ps1 doctor` reports the VM's toolchain without changing anything, `remote.ps1 shell` opens a shell in the shipped tree, `remote.ps1 clean` drops the VM's cargo target cache. See `docs/windows-vm-ci.md`. `ci\windows\ci.ps1` is those same steps run natively — it installs nothing and changes no machine state, so it can also be run directly on a Windows dev box when the ssh round trip isn't wanted.
- Do **not** reach for `.github/workflows/windows-ci.yml` to find out whether something works: it needs a commit and a push to trigger, and it is slow even warm because a GitHub runner starts with cold caches every time. It runs itself on push/PR — read it after the fact, don't drive it. `ci/windows/ci.ps1` mirrors its steps; when the two disagree, the workflow is right and `ci.ps1` is stale.
